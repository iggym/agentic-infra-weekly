Harness Over Horsepower

July 2025 · 8 min read

Wrong Bottleneck

In mid-2023, researchers at UC Berkeley's Sky Computing Lab hit a wall that every AI platform team would soon recognize. They were serving large language models for Chatbot Arena, the popular model-comparison platform run by LMSYS, and throughput was the bottleneck — not the model's quality. The GPUs were spending most of their time managing memory for the key-value cache that stores conversation context, not computing tokens. The model was fine. The serving harness was the problem.

Woosuk Kwon and his collaborators published a solution they called PagedAttention, which treats the KV cache like virtual memory pages in an operating system — allocating and freeing memory dynamically instead of reserving fixed blocks for each request. The result was vLLM, an open-source serving engine that delivered 2–4× throughput improvements over existing solutions. Same models. Same GPUs. Different harness. LMSYS deployed vLLM for Chatbot Arena, and the project quickly became one of the most-starred LLM serving repositories on GitHub.

The lesson wasn't subtle. The model was identical before and after. What changed was the infrastructure around it — the harness that decides how to allocate memory, batch requests, and manage compute. The model was a commodity. The harness was the differentiator.

The Moat's the Harness

Here's the reframe: in AI systems, the model is a replaceable dependency. The harness — your routing logic, fallback patterns, cost controls, and reliability layer — is the actual product. This isn't abstract. LiteLLM, which provides a unified API for routing requests across 100+ LLM providers, has accumulated over 15,000 GitHub stars precisely because teams have realized that the routing layer is where the real engineering lives. Companies like Anyscale built their entire commercial offering around this insight: their Ray Serve platform manages model serving, routing, and scaling — the harness, not the model.

A model is a library dependency with a per-token license fee.

Hidden in Plain Sight

Model routing and SRE error budgets are the same practice wearing different name tags. When you decide which model handles which query, you're making a capacity planning decision — allocating your most expensive compute to the requests that need it most. When you set a fallback from GPT-4 to GPT-4o-mini, you're implementing a circuit breaker. When you cap daily token spend, you're enforcing an error budget. These aren't new ideas. They're SRE principles applied to a new domain.

The vLLM story illustrates this precisely. PagedAttention is a memory management technique borrowed from operating systems — virtual memory paging, applied to GPU memory. The insight wasn't a new model architecture. It was a systems engineering insight applied to the serving layer. The same pattern appears in LiteLLM: its most valuable feature isn't the API abstraction (that's a convenience), it's the routing logic that lets you specify complexity thresholds, cost caps, and fallback chains — all SRE concepts.

Anyscale takes this further. Their Ray Serve architecture implements progressive delivery for models: deploy a new model version, route 5% of traffic to it, compare latency and quality metrics, and gradually shift — exactly like a canary deployment for a microservice. The methodology is GitOps reconciliation with canary rollouts, applied to model serving.

Where the Rubber Meets

Every claim here rests on a specific, documented system. The vLLM throughput numbers come from the PagedAttention paper published by Kwon et al. at UC Berkeley. The LiteLLM adoption data is from its public GitHub repository. The Anyscale architecture is documented in their conference talks and engineering blog posts, including presentations at Ray Summit.

The systems-thinking methodologies at work: vLLM uses resource management (virtual memory paging) as a systems optimization. LiteLLM implements circuit breakers and cost budgets as routing controls. Anyscale applies canary rollouts and progressive delivery to model deployment. In each case, the methodology accounts for the outcome — the harness, not the model, determines production performance.

The strongest counterargument: models are getting cheaper and more capable, so the routing overhead isn't worth it. Here's the response: cheaper models enable more use cases, which means more traffic, which means more routing decisions, which means more potential for the wrong routing to cost you — in money, latency, or reliability. The cost of routing overhead is fixed; the cost of not routing scales linearly with traffic.

Take the Wheel

1. Audit your routing distribution. Pull last month's API logs and calculate what percentage of your spend went to your most expensive model for queries that a cheaper model could handle. If you don't have routing data, you've found your first problem. RouteLens — a lightweight model router on Cloudflare Workers — can give you this visibility in an afternoon.

2. Run a canary model test. Route 10% of your traffic to a cheaper model and compare quality metrics. If you can't measure the quality difference, the cheaper model is good enough for 100% of that traffic category. CostScope tracks the cost impact automatically.

3. Set cost circuit breakers. Implement daily and per-request token limits. If a single request exceeds your threshold, fall back to a cheaper model or return an error. This is standard SRE practice — you're applying it to LLM costs instead of CPU usage.

4. Build your routing harness. Start with a simple complexity classifier — even a prompt-length heuristic — and route accordingly. Then iterate. The harness evolves; the model gets swapped. HarnessBuilder generates initial routing configurations from natural language descriptions.

First 24 Hours

Open your LLM provider's usage dashboard right now. Find the percentage of requests that went to your most expensive model in the last 30 days. Then ask: what fraction of those requests actually needed that model's capabilities? That gap — between what you paid for and what you needed — is the exact size of your harness problem.
