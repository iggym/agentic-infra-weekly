The Automation Trap

The Engine of Outages

The dashboard glowed an angry, solid red. At DoorDash, engineers watched as their Kubernetes API servers throttled into oblivion, taking down critical microservices across their massive delivery platform. The enemy wasn't a traffic spike from the Super Bowl or a rogue infrastructure engineer running a destructive script. The culprit was their own automation. Specifically, the relentless, unthrottled reconciliation loops of their GitOps deployment systems were hammering the control plane, generating an overwhelming tide of API requests that pushed the cluster into cardiac arrest. The machine designed to keep the platform stable had become the instrument of its destruction.

Loops Burn Budgets

This brings us to a harsh truth about modern platform engineering.

GitOps doesn't prevent outages; it automates them. For years, we’ve championed declarative infrastructure and continuous reconciliation as the pinnacle of operational reliability. We treat the reconciliation loop as a safety net. But the safety net is on fire. When a GitOps tool like ArgoCD or Flux detects a configuration drift, it acts with mechanical, unyielding aggression to correct it. If the desired state is unattainable, or if a custom controller enters a hot-loop—exactly as Shopify experienced when a misconfigured custom resource triggered a reconciliation storm that DDoS-ed their own internal control planes—the automation becomes a highly efficient outage engine.

The bold reframe is this: reconciliation loops are not safety nets. They are autonomous agents that require strict, defensive rate-limiting. We have built self-driving cars without brakes.

Speed Bends Both Ways

We assume that faster delivery and faster remediation inherently improve reliability. If a pod crashes, the operator immediately spins up a new one. If a config drifts, GitOps re-applies the manifest. But this masks a hidden connection between automation speed and blast radius.

Your speed of recovery is now bound by your speed of destruction.
Reconciliation Storm Simulator

When Shopify’s custom controller began rapidly reconciling, the sheer volume of API calls saturated the Kubernetes control plane. The system’s natural dampeners—cache delays, API priority, scheduling queues—were bypassed by a flood of automated intent. By treating their own internal control planes as untrusted, rate-limited public APIs and implementing exponential backoffs, Shopify applied defense-in-depth to their automation. They recognized that an automated system operating without backpressure is just an optimized weapon.

Credibility And Nuance

The counterargument is obvious: GitOps ensures desired state, so it is inherently safer than manual kubectl apply commands. It prevents configuration drift and standardizes deployments. This is true, but it misses the operational reality. Desired state is a liability when the desired state is wrong.

When an engineer pushes a bad manifest, the GitOps controller doesn’t pause to ask if the manifest makes sense. It enforces it. It re-applies it. It fights the Kubernetes scheduler to the death. As documented by DoorDash, the continuous deployment systems themselves became the primary consumers of cluster resources, degrading overall system reliability and forcing the team to implement API priority and fairness limits just to protect the control plane from their own tooling. The SRE error budget wasn't being burned by user traffic; it was being burned by ArgoCD aggressively trying to reconcile thousands of resources simultaneously.

The systems-thinking methodology at work here is a breakdown of the Four Golden Signals. By hyper-focusing on deployment frequency (a DORA metric), teams ignore saturation. They fail to account for the fact that every reconciliation loop is an API call, and every API call has a cost.

Throttle The Machine

If GitOps is an outage engine waiting to redline, you must install a governor. You have the agency to fix this.

First, implement API Priority and Fairness on your Kubernetes control planes. Stop treating your automation tools as trusted, well-behaved tenants. Treat them as potentially hostile actors that must be rate-limited. Give your GitOps controller's service account a low priority. If the control plane is under stress, the automation should be the first thing throttled, not the last.

Second, audit your reconciliation intervals. Does ArgoCD really need to poll Git every 30 seconds? Does your custom controller need to reconcile every 15 seconds? Extend those timers. Introduce jitter. The DoorDash incident proved that scaling back aggressive polling is a higher-leverage reliability action than scaling up the control plane.

Finally, integrate pre-flight validation using tools like GitOps Guardian. Before a manifest hits the cluster and triggers a destructive loop, scan the pull request for high-risk configurations. Use AI-driven linters to flag missing SyncOptions or overly aggressive rolling update strategies.

Cap The Damage

Automation without boundaries is just a faster way to fail. Your GitOps tools are not infallible guardians; they are blunt instruments applying brute force to complex systems.

Within the next 24 hours, open your ArgoCD or Flux configuration and double the syncTimeout and requeue values. Force your automation to take a breath. Give your error budget a chance to survive.
