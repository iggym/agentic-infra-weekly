Mind the Gap

Why your model routing layer is the real production bottleneck — not the models themselves.

Opening Scene

On November 8, 2023, OpenAI's API went dark for hours. Every application that had hard-coded GPT-4 calls — no fallback, no cache, no alternative — showed its users error messages and spinning wheels. Meanwhile, teams that had built routing layers in front of their LLM calls fell back to Anthropic's Claude or Google's Gemini within milliseconds. Same outage. Completely different customer experience. The difference wasn't which model they'd chosen. It was whether they'd built the plumbing between the request and the response.

Harness Over Horse

Your model isn't your moat. Your routing layer is. The infrastructure that decides which model handles which request, when to cache a response, when to fall back to a cheaper provider, and when to reject a request outright — that's what determines whether your AI features are profitable, reliable, or even usable at scale. The model is the engine. The routing layer is the transmission. Nobody brags about their transmission, but you can't drive without one.

Cloudflare saw this gap early. Their AI Gateway product, launched in beta in 2023 and expanded through 2024, sits between applications and LLM APIs and provides caching, rate limiting, fallback routing, and per-request analytics. Cloudflare reported that over 100,000 developers routed LLM requests through the gateway within months of general availability [Cloudflare Blog, 2024]. The product isn't a model. It's not a framework. It's the plumbing that makes models work in production — and the adoption numbers prove the plumbing was missing.

The vLLM project at UC Berkeley demonstrated the same principle from a different angle. Their PagedAttention paper, published in 2023, showed that the bottleneck in LLM inference wasn't compute power — it was GPU memory management. By treating GPU memory like a virtual memory system with paging, vLLM achieved 2–4x throughput improvements over existing serving engines without changing the model at all [Kwon et al., 2023]. Roblox and Anyscale adopted vLLM for production inference, running it on Kubernetes with Ray Serve orchestrating GPU workloads on NVIDIA A100s and H100s. The insight: you can throw bigger GPUs at the problem, or you can fix the serving layer. The serving layer is cheaper and faster.

Hidden Wires

These stories — a gateway product, a memory management paper, an outage that separated the prepared from the unprepared — look like different problems. They're not. They're all the same problem: the gap between model capability and production reality.

We treat model selection as the architectural decision. It's not. Model selection is a configuration choice. The architectural decision is what sits between your user's request and the model's response.

The routing layer is the real API contract.

When you think of your routing layer as the API contract — the thing that guarantees latency, cost, and availability — you stop building features that depend on a specific model and start building features that depend on a specific capability. The model becomes swappable. The routing layer becomes the foundation.

The November 2023 OpenAI outage proved this in production. Companies that had built routing layers with circuit breakers — automatic fallback to Anthropic or Google when OpenAI returned errors — maintained service throughout the outage. LiteLLM, the open-source proxy providing unified access to over 100 LLM providers, saw a significant adoption surge in the weeks following the outage, reflected in GitHub stars, issues, and community discussion volume [LiteLLM GitHub, 2023]. Not because teams wanted more models. Because they wanted their features to survive.

Yes, But...

The strongest counterargument: "GPT-4 is better than GPT-3.5, and routing to a cheaper model degrades quality." True — for the hardest 15% of requests. For the other 85%, the quality difference is negligible and the cost difference is 10–30x. A routing layer that classifies request complexity and routes accordingly doesn't degrade quality — it preserves quality where it matters and saves money where it doesn't. The counterargument assumes all requests are equal. They're not.

Pave the Path

  1. Audit your LLM call distribution. Pull the last 30 days of API logs. For each request, log the model called, token count, latency, and whether the response complexity justified the model. You'll likely find that most of your spend goes to simple requests hitting expensive models. LiteLLM's proxy can generate this audit in an afternoon.
  2. Build a three-tier routing rule. Classify incoming requests into simple (route to the cheapest capable model), moderate (mid-tier), and complex (your best model). You don't need ML to classify — prompt length and task type are usually sufficient. Deploy this as a Cloudflare Worker in front of your existing API calls.
  3. Add a circuit breaker. If your primary LLM provider returns three consecutive errors or exceeds your latency budget, automatically fall back to a secondary provider. Cloudflare AI Gateway provides this out of the box; LiteLLM provides it in open source.
  4. Instrument your routing layer. Add per-request metrics: model called, cost, latency, fallback triggered. Feed these into your existing observability stack — Prometheus, Datadog, or whatever you already run. You can't optimize what you can't see.

Close the Gap

Open your LLM provider's usage dashboard right now. Sort by cost. Look at the top ten most expensive requests. Ask: did that request need GPT-4? If the answer is "I don't know," you've found your gap. Close it.
