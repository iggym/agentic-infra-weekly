Same Weights, Worse Answers

Oct 7, 2026 · 5 min read

Nobody Touched the Model

In August 2025, developers started saying the same thing in forums and on social media: Claude felt worse. Answers drifted. Code suggestions got sloppier. Some English responses suddenly contained Thai or Chinese characters. The usual explanation spread quickly: the provider must have quietly swapped in a cheaper model to save money.

On September 17, Anthropic published a postmortem that told a different story[1]. Nobody had swapped the model. The weights were the same. Instead, three separate infrastructure bugs had overlapped in time, each one degrading output quality in a different way, on different hardware and for different models.

One was a routing error that sent some Sonnet 4 requests to servers configured for a different context window. At its worst hour, on August 31, it affected 16% of Sonnet 4 requests. A second was a misconfiguration on TPU servers that occasionally gave high probability to tokens that should almost never appear. That was the source of the stray Thai and Chinese characters. The third was a compiler bug in an approximate top-k operation on TPUs, which silently changed which tokens the model could pick from.

None of the three changed a single parameter of the model. All three changed what users got back.

Quality Is a Serving Property

Model quality is an infrastructure SLO. The weights didn't change; the serving stack did. If your evals only run before deploy, you can't see the failures that actually ship.

Most teams treat model quality as a property of the model: you pick a model, run a benchmark, and the score is the score. Infrastructure is treated as a pipe that either delivers tokens or doesn't. That's a category error. A model in production is a pipeline: a router, a sampler, a compiler, a set of kernels, and a hardware fleet that may span several chip types. Every stage can quietly change the output distribution while every dashboard stays green.

Latency, error rate, and throughput tell you whether the pipe is flowing. They tell you nothing about whether the right thing is flowing through it.

A 200 OK with a wrong answer is still an outage. It just doesn't page anyone.

SRE Already Has a Word for This

Site reliability engineering solved a version of this problem long ago. Google's SRE book defines service level indicators as measures of what users actually experience, not what the servers report[2]. A storage system whose disks are healthy but returns corrupted reads is down, whatever its uptime graph says. SREs call this a correctness SLI, and mature storage and data teams measure it with probes: write a known value, read it back, compare.

The same book draws a line between black-box monitoring, which tests the system from the outside the way a user would, and white-box monitoring, which watches internal metrics[3]. AI serving stacks today are heavy on white-box signals (GPU utilization, tokens per second, queue depth) and nearly empty on black-box correctness probes.

The translation is direct:

  • Known-answer probes become a small, fixed set of prompts with checkable outputs, sent continuously through the production path.
  • Per-replica correctness becomes running those probes against each hardware pool and serving configuration separately, because a bug on one chip type disappears in a fleet-wide average.
  • Error budgets become quality budgets: an agreed threshold of probe failures that triggers rollback, the same way a 5xx spike would.

Why It Took Weeks

The postmortem is unusually candid about why detection was slow[1]. Anthropic's validation relied on benchmarks, safety evaluations, and performance metrics, and those evaluations "simply didn't capture the degradation users were reporting." The bugs overlapped, so user reports pointed in contradictory directions. Each bug hit different models on different platforms. Privacy controls that limit engineers' access to user conversations, the right default, also meant engineers couldn't easily inspect the bad outputs.

The fixes Anthropic committed to are an SRE playbook. They include evaluations designed to tell working implementations from broken ones, continuous quality monitoring on production systems rather than only before release, and better debugging tools that respect user privacy.

Notice what was missing before: a correctness signal measured where users are, broken down by serving path. Every one of the three bugs lived in a specific slice (a router rule, a chip type, a compiler path). Fleet-wide benchmarks averaged them away. Per-path probes would have shown them as separate lines bending away from baseline.

Grain of Salt

The fair objection: LLM output isn't deterministic, so "known-answer" probes are noisy, and continuous evals cost real money. You can't run a full benchmark suite against production every minute.

True, and you don't need to. Correctness probes work by statistics, not single answers. Fifty prompts with verifiable outputs (arithmetic, structured extraction, code that compiles, a language-ID check on the reply) produce a pass rate. A pass rate per serving path, sampled every few minutes, is cheap and stable enough to alert on. The cost is a rounding error next to a multi-week quality incident.

What would prove this thesis wrong? If degradation always showed up first in latency or error metrics. Here it didn't: the routing bug, the sampling corruption, and the compiler bug all returned well-formed, on-time responses.

Probe the Pipe

  1. Write 30–50 canary prompts with checkable answers. Mix arithmetic, JSON extraction against a schema, a short code task you can execute, and a "reply in English" check that flags unexpected scripts. Keep them stable. Changing them resets your baseline.
  2. Send them through the real production path. Use the same gateway, auth, routing rules, and model settings as user traffic, not a side door. Tag each request with the serving path it took.
  3. Record pass rate as a metric, broken down by path. Use OpenTelemetry's generative-AI semantic conventions so model, provider, and operation attributes are consistent across services[4]. Chart pass rate per model, region, and provider.
  4. Set a quality budget and wire it to rollback. Decide what pass-rate drop counts as an incident, and treat it exactly like an error-rate breach: page, freeze rollouts, and roll back the last serving change.
  5. Open a user-report channel that feeds triage. In Anthropic's case, user reports were the earliest signal. Give "this feels worse" reports a structured form with model, time, and example, and review them alongside the probe data.

First 24 Hours

Pick ten prompts your product depends on and that have answers you can check automatically. Run each one twenty times against production right now and record the pass rate. Save the numbers. Tomorrow you'll have a baseline, and you'll be able to tell "the model feels off" from "the model is off."
