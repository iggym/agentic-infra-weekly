The Desired State Delusion

In November 2023, engineers at OpenAI pushed a new Kubernetes service to production. Within minutes, the platform buckled. ChatGPT went dark for hours. The root cause wasn't a malicious attack or a corrupted database; it was the system trying to enforce "desired state" too aggressively. The new service spammed the Kubernetes API server with requests, overwhelming the control plane and triggering a cascading failure across the entire infrastructure.

This wasn't a freak accident. It was a symptom of a systemic blind spot in modern platform engineering.

GitOps isn't pulling your infrastructure closer to desired state; it's accelerating drift by treating infrastructure as version-controlled code rather than ephemeral state.
Old Model: Git as Source of Truth New Model: State as Source of Truth

The Hidden Cost

We have been sold a lie. The promise of GitOps and declarative infrastructure is that if you define the perfect state in Git, the system will continuously pull reality toward that state. But this ignores the physical realities of distributed systems. Control planes have limits. API servers can drown. When a reconciler tries to force a massive state change instantly, it doesn't converge—it shatters.

Consider the March 2023 outage at Datadog. A routine rollout of the Datadog Agent across their Kubernetes clusters led to a massive platform outage. A misconfiguration in the agent's reconciliation logic caused every agent to simultaneously query the Kubernetes API server for pod metrics. The API servers buckled under the thundering herd of requests, leading to cluster instability. The systems-thinking methodology at work here was an insufficient application of progressive delivery. The blast radius was massive because the rollout lacked strict canary phases and backoff logic in the agent's polling mechanism. Treating infrastructure components as stateless apps that can be instantly updated ignores the API-limited nature of Kubernetes control planes.

Control Loops Need Brakes

Months later, Mercari experienced a variation of the same nightmare. A single Git commit updating an ArgoCD ApplicationSet triggered the generation and immediate reconciliation of thousands of Application resources simultaneously. The ArgoCD controller ran out of memory and crashed, halting all deployments across the organization. Mercari's failure was a missing application of blast radius limitation and error budgets. There was no rate limiting on Application generation. A single repo change consumed 100% of the deployment controller's resources.

A control loop without backoff is just a self-inflicted DDoS.

The hidden connection here lies in control theory. A thermostat doesn't blast heat continuously until it hits the exact degree; it uses hysteresis to prevent short-cycling. Kubernetes controllers and GitOps operators lack this inherent hysteresis. They treat Git as an imperative mandate disguised as a declarative ideal. When the delta between actual state and desired state is large, the reconciler becomes a weapon.

Auditability Is Not Availability

The strongest counterargument to this reframe is that GitOps provides essential auditability and security through pull-based reconciliation. Auditability means nothing if the platform is down. A perfectly audited Git history of a crash-looping controller is cold comfort to an engineer on call at 3 AM. We must prioritize availability over absolute state purity.

Take Back The Reins

To fix this, platform engineers must take back the reins from the reconciler. First, implement rate limiting and exponential backoff on your controllers. Do not allow a single Git commit to trigger thousands of simultaneous API calls. Second, introduce progressive delivery to your GitOps pipelines. Canary your syncs the same way you canary application code. Third, leverage AI-driven observability tools like PostMortem.ai to detect sync storms before they become outages.

Stop trusting the reconciler to magically resolve your infrastructure. Treat the path from Git to live state as a fragile, rate-limited channel that requires careful traffic shaping.
