Automating the Wrong Thing

Manual Outage Automated Outage (GitOps)

Tail Wags The Dog

On a quiet Tuesday afternoon, an engineer at DoorDash merged a standard configuration pull request. The CI pipeline ran green. ArgoCD synced the change instantly to the production cluster. Within minutes, every single API request returned a 404 error. The platform was completely down. The GitOps dashboard proudly displayed a perfectly synchronized state. The system was working exactly as designed, and it was destroying the business.

We adopted GitOps to make deployments safer. The promise was simple: declarative infrastructure, version-controlled state, and automated reconciliation. But we bought a lie.

Automating The Wrong Thing

GitOps doesn't prevent outages; it just automates how fast you can break everything.

Engineers treat a green ArgoCD or Flux dashboard as proof of system health. It is not. It is only proof that the cluster state matches the Git repository. When DoorDash pushed that flawed Envoy configuration in May 2023, their AWS EKS cluster obediently applied it via ArgoCD. The reconciliation loop did its job. But because the pipeline lacked progressive delivery constraints, the configuration rolled out globally in seconds. The system trusted the manifest, skipped the canary, and took down the entire platform.

The hidden danger in Kubernetes DevOps is that we have optimized the deployment mechanism without securing the deployment payload. We assume that because the delivery is automated, the content is safe.

Blind Spots In Loops

A green ArgoCD dashboard is not a green system; it's just a synchronized failure.

Consider GitLab’s 2023 degradation incident. Background processing jobs began consuming massive amounts of memory. The root cause? The default Helm chart used to deploy Sidekiq on their Google Kubernetes Engine cluster lacked hard memory limits. When traffic spiked, pod memory exploded. Without boundaries, the Kubernetes scheduler thrashed, evicting pods and causing cascading failures across GitLab.com.

The Helm chart was syntactically valid. The GitOps pipeline applied it successfully. Yet, the operational reliability of the platform was fundamentally compromised by a missing default. We are connecting Git repositories to clusters, but disconnecting engineering teams from the actual runtime constraints of their software.

Pulling The Reins Back

The counterargument is obvious: "GitOps combined with CI tests catches these issues." But CI tests check schema and syntax, not runtime behavior or network topology. A unit test won't flag an Envoy route that drops 100% of traffic, and a lint check won't fix a Sidekiq pod starving a node of memory.

To build reliable platforms, we must stop treating deployment automation as a substitute for operational rigor. You cannot engineer your way out of bad defaults with faster loops.

Engineers must regain narrative agency over their infrastructure. First, decouple configuration changes from application deployments in your GitOps pipelines, enforcing strict canary rollouts for edge configurations. Second, audit every default Helm chart for missing resource limits and probes before it ever touches a production node. Third, implement blameless postmortems that specifically investigate why the GitOps pipeline allowed a bad state to pass, rather than just fixing the bad state itself.

Don't Trust, Verify

Operational reliability in Kubernetes doesn't come from faster synchronization. It comes from the friction we deliberately inject into the pipeline to protect us from ourselves.

Pick one critical service in your cluster today. Go to its ArgoCD Application manifest and add a strict, automated canary rollout stage that requires Datadog error rates to remain below threshold before progressing. Stop trusting your Git state, and start verifying your runtime.
