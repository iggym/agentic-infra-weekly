The File That Fit Yesterday

Oct 7, 2026 · 5 min read

Sixty Features, Then Two Hundred

At 11:05 UTC on November 18, 2025, Cloudflare rolled out a routine permissions change to a ClickHouse database cluster[1]. It was the kind of change that ships every week: tightening how users see the tables they can already access.

Fifteen minutes later, Cloudflare's network started returning HTTP 5xx errors to a large share of the internet.

The chain went like this. Every five minutes, a job queried that ClickHouse cluster to build a "feature file" for Cloudflare's Bot Management system: the list of signals its machine-learning model uses to score traffic. The file normally held about 60 features. After the permissions change, the query started returning rows from a second, underlying database as well, so the list had duplicates. The file more than doubled. The core proxy that loads it had a hard limit of 200 features, preallocated for performance. The new file blew past it, and the proxy code hit an unhandled error and panicked[1].

Then it got strange. Because the database cluster was being updated gradually, each five-minute run had a chance of landing on an updated node or an old one. The network flapped between a good file and a bad one, failing and recovering, which looked a lot like an attack. Core traffic wasn't flowing normally again until 14:30, and everything was fully restored at 17:06[2].

Config Is a Deploy

Generated config is a deploy that skips your deploy pipeline. If a file can take down production, it needs the same canary, validation and rollback as code.

Most organizations draw a hard line between code and configuration. Code goes through review, tests, staged rollout, and a rollback button. Configuration, especially configuration that a machine regenerates on a timer, is treated as data. It flows straight to production, often to the whole fleet at once, because it's "just a file."

That line is a fiction. If a file changes what a running program does, it's part of the program. The only difference is that it skipped the gates you built for every other kind of change.

Your deploy pipeline protects you from the changes that go through it.

We've Seen This File Before

Cloudflare's incident has a famous older sibling. On July 19, 2024, CrowdStrike pushed a content update for its Falcon sensor: a configuration file called Channel File 291, not a code release[3]. The sensor's content interpreter read past the end of an array while parsing it. The exception couldn't be handled in kernel mode, and about 8.5 million Windows machines crashed into boot loops. The sensor code had been tested. The content file was validated by a validator that had its own bug. Then it went out everywhere at once.

Three years earlier, on October 4, 2021, Facebook disappeared from the internet for about six hours[4]. A command meant to assess backbone capacity took down all the backbone connections, and an audit tool that should have blocked it had a bug. With the backbone gone, Facebook's DNS servers withdrew their own BGP routes, which made the outage harder to fix.

Different companies, different files, the same shape:

  • A change that wasn't classified as a deploy, so it skipped staged rollout.
  • A consumer that trusted its input and turned bad data into a crash instead of a rejection.
  • A global blast radius, because config propagates faster than code by design.

Google's SRE workbook names the missing practice directly. Canarying, it argues, applies to any change that can affect production, explicitly including configuration changes[5].

The Fixes on the Record

Cloudflare's own remediation list reads like a definition of "treat config like code"[1]. It includes hardening ingestion of Cloudflare-generated configuration files the same way user-generated input would be, adding more global kill switches for features, and reviewing failure modes for error conditions across all core proxy modules. In plain terms: validate it, be able to turn it off quickly, and don't crash on it.

The detail worth dwelling on is the limit. The proxy had a sensible guard: preallocate memory for at most 200 features. The guard wasn't the bug. The bug was what happened when the guard tripped. The process died instead of rejecting the new file and continuing with the last good one. A limit that crashes the program is just a tripwire.

The systems-thinking methods here: staged rollout limits how far a bad change spreads before you notice. Last-known-good fallback turns bad input into a logged rejection instead of an outage. Schema and bounds validation at the producer catches the doubled file before it ever leaves the generator.

Grain of Salt

The counterargument is speed. Bot-detection features and threat signatures have to change fast. Attackers adapt in minutes, and a canary that takes an hour defeats the purpose. That's exactly why these files were on a fast path.

It's a real tension, but a canary doesn't have to be slow. Rolling a file to 1% of machines and watching crash rates and error rates for two minutes before going to 100% would have caught both the Cloudflare and CrowdStrike files. Neither bug was subtle once it reached a real host. The goal isn't to slow config down to code speed. It's to make sure no single change reaches every machine before any machine has survived it.

Put It in the Pipeline

  1. Inventory machine-written config. List every file, flag, rule set, or model artifact that's generated by a job and consumed by a production service: feature lists, routing tables, allowlists, ML features, policy bundles. Note how often each one changes and how it reaches production.
  2. Validate at the producer. Before publishing, check the schema, row counts, and size against the previous version. A file that's suddenly twice as big, or has duplicate keys, should fail to publish and page its owner.
  3. Make consumers keep the last good file. On parse failure or limit breach, reject the new file, keep serving with the previous one, and emit a loud metric. Search your code for places where loading config can panic or exit, and fix them first.
  4. Canary config like code. Push to a small slice of the fleet, watch crash and error rates, and promote automatically if they hold. In Kubernetes, tools like Argo Rollouts or Flagger can drive progressive delivery for config held in ConfigMaps when you version them with the workload[6].
  5. Add a kill switch per feature. Every config-driven feature should be disable-able on its own, globally, in seconds, without a deploy.

First 24 Hours

Find the single config file in your stack that's regenerated most often and loaded by the most machines. Copy it, double every entry in it, and load it into a staging instance of its consumer. Does the service reject it and carry on, or does it fall over? Either way, you now know which side of the Cloudflare postmortem you're on.
