The Deputy Takes Dictation

Oct 7, 2026 · 6 min read

One Issue, Two Repos

In late May 2025, researchers at Invariant Labs published a short, uncomfortable demo[1]. The target was the official GitHub MCP server, the integration that lets an AI agent read issues, browse code, and open pull requests on your behalf. It had roughly 14,000 stars at the time. Nothing about it was misconfigured. Its tool descriptions were clean, and its code did exactly what it promised.

The attack needed one thing: a GitHub issue. The attacker opened it on a public repository owned by the victim. The issue text contained instructions written for an AI agent rather than for a human maintainer. Then they waited.

Eventually the victim did something ordinary. They asked their agent to take a look at the open issues on that public repo. The agent fetched the issues, read the planted text, and followed it. It used the victim's own GitHub credentials to read data from the victim's private repositories. Then it published that data in a pull request on the public one. Every action was authorized. Every API call was legitimate. The agent was doing its job, just for the wrong person[2].

Invariant called it a "toxic agent flow." The trade press called it a vulnerability with "no obvious fix." Both were right. The second is only true if you keep looking for the fix in the wrong place.

Wrong Bug, Right Name

Prompt injection isn't an input-filtering bug. It's the confused deputy problem from 1988, and the fix is the same one: give the agent less authority, not better instructions.

Most teams treat prompt injection like SQL injection: find the bad strings and escape them. That framing assumes there is a reliable boundary between code and data inside the model. There isn't. A language model reads everything in its context window as potential instructions, whether it came from your system prompt, your user, or a stranger's GitHub issue. Filters and "ignore previous instructions" detectors reduce the odds. They can't close the hole, because the hole is the product feature: the model follows natural-language instructions.

So stop asking how to make the model refuse bad instructions. Ask the question security engineers settled decades ago: whose authority is this program using, and on whose behalf?

An agent is a program that takes dictation from anyone who can get text in front of it.

Hardy's Compiler

In 1988, Norm Hardy described a bug from a timesharing system he had worked on[3]. The system's compiler was allowed to write to a billing file, because it recorded usage statistics there. Users could also tell the compiler where to write its output. One user named the billing file as the output file. The compiler, holding write permission it had been given for an entirely different reason, overwrote the billing records.

Hardy called the compiler a confused deputy. It acted with authority from two sources: its own (for billing) and the user's (for output). It had no way to tell which authority a given request should use. His conclusion was not "validate filenames harder." It was that authority should travel with the request, as a capability, so the program can only touch what the requester could have touched.

Map the GitHub demo onto Hardy's paper and it lines up almost exactly:

  • The deputy is the agent, holding a token that can read every repo the user can.
  • The first principal is the user, who wanted a summary of public issues.
  • The second principal is the attacker, who can write text the agent will read.
  • The confusion is that the agent spends the user's authority on the attacker's request.

Simon Willison, who coined the term "prompt injection" in 2022[4], later boiled the dangerous setup down to a "lethal trifecta": access to private data, exposure to untrusted content, and a way to communicate externally[5]. That's Hardy's deputy, restated for LLMs. Private data is the authority. Untrusted content is the second principal. External communication is the billing file. Remove any one leg and the exfiltration path breaks, whether or not the model was fooled.

What the Record Shows

The details matter, so here they are. Invariant's write-up shows the attack working against an unmodified GitHub MCP server through a mainstream agent client. The malicious payload lived entirely in an issue on a public repository. The leak landed in a pull request the agent created itself[1]. Coverage at the time stressed that this was not a bug in GitHub's code. It was an architectural property of giving one agent broad credentials and untrusted input at the same time[2].

OWASP has ranked prompt injection as the number-one risk in every edition of its Top 10 for LLM applications, including the 2025 list[6]. Its guidance leads with privilege control and human approval for high-risk actions, ahead of input filtering. That ordering is the tell: the people who catalog these failures have concluded that you contain injection rather than prevent it.

The systems-thinking methods at work here are old ones. Least privilege limits what the deputy can spend. Capability-based design ties authority to the request instead of the process. Information-flow control stops data labeled private from reaching a public sink. None of them depend on the model behaving.

Grain of Salt

The strongest counterargument: models are getting much better at resisting injection, and narrowly scoped agents are less useful. If the agent needs a new token for every repository, nobody will use it.

Both points are fair. Resistance training does raise the attacker's cost, and friction is real. But "the model will probably refuse" is a probabilistic control guarding a deterministic asset. A 99% refusal rate across millions of agent sessions still means a steady stream of successful attacks, and the attacker gets unlimited retries for the price of a GitHub issue. Scoping doesn't have to be painful, either. A per-task token that's minted automatically costs the user nothing.

What would prove this thesis wrong? A model architecture that keeps instructions and data in separate, enforced channels. Until one ships and survives red-teaming, plan as if every token in the context can give orders.

Revoke the Badge

  1. Inventory your trifectas. List every agent and MCP server you run. For each, mark whether it can read private data, whether it ingests text from outside your trust boundary (issues, emails, web pages, tickets), and whether it can write somewhere others can see. Any row with all three marks is a live exfiltration path today.
  2. Scope credentials to the task, not the user. Swap classic personal access tokens for GitHub fine-grained tokens limited to the specific repositories an agent needs[7]. An agent that triages public issues should not hold a token that can read private repos.
  3. Split agents by trust domain. Run one agent instance that reads untrusted content and has no private-data access, and a separate one with private access that never sees untrusted text. Pass only structured, validated results between them, such as issue numbers rather than issue bodies.
  4. Gate the external leg. Require human approval for write actions that cross a visibility boundary: opening a public PR, posting a comment, sending an email, or calling an outbound URL. Turn off any "always allow" setting for those tools.
  5. Log tool-call sequences, not just tool calls. A private-repo read followed by a public write in the same session is a signal worth alerting on, even when each call on its own is fine.

First 24 Hours

Open the config for every MCP server your team uses and write down the credential each one runs with. For each credential, answer one question: if a stranger could send this agent a paragraph of text, what is the most private thing it could read and the most public place it could write? If the answer to both is "a lot," you've found the token to rotate first.
