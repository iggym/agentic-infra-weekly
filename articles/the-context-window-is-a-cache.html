AI Platform Architecture · Week 41

The Context Window Is a Cache

Oct 7, 2026 · 6 min read

150,000 Tokens of Menu

In November 2025, Anthropic's engineering team published a worked example that should make every agent platform team wince[1]. An agent connected to MCP servers is asked to download a meeting transcript from Google Drive and attach it to a Salesforce lead. A simple job. The way most agents are wired, it goes like this.

First, the definitions of every tool from every connected server are loaded into the model's context before the agent does anything. Then the agent calls the Drive tool, and the full transcript comes back into context. Then the agent calls the Salesforce tool and has to write that same transcript out again as the tool's input, token by token. The document passes through the model twice, and the model doesn't need to reason about any of it. For a two-hour sales meeting, Anthropic estimates that's an extra 50,000 tokens[1].

The alternative has the agent write a few lines of code that call the tools directly, inside a sandbox. Tool definitions are stored as files the agent can browse and load only when needed, and the transcript moves from one API to the other without entering the model's context. For the tool definitions alone, Anthropic reported that loading only what the task needs instead of everything up front cut token use from 150,000 to 2,000, a 98.7% reduction[1].

Two months earlier, Cloudflare had published nearly the same finding under the name "Code Mode"[2]. Two teams, separately, had arrived at the same conclusion: the context window was being used wrong.

Treat It Like L1

The context window isn't a prompt; it's the scarcest tier in your memory hierarchy. Loading every tool definition up front is like copying the whole disk into L1.

Teams still talk about context as "the prompt": a document you write, then stuff with whatever might help. As windows grew to hundreds of thousands of tokens, the instinct was to fill them. Every tool, every doc, every prior message, just in case.

But context is not storage. It's the most expensive, most contended, slowest-to-fill memory your system has. You pay for it on every call, it adds latency on every call, and its quality degrades as it fills. Computer architects learned to manage exactly this kind of memory decades ago.

Every token in context is rent you pay on every turn.

The Memory Hierarchy, Again

Every computer has a memory hierarchy: a small amount of very fast memory close to the processor (registers, L1 cache), backed by larger, slower tiers (L2, RAM, disk). Performance comes from keeping the working set in the fast tier and fetching everything else on demand. Nobody copies the whole disk into L1 at boot.

Map an agent onto that model and the anti-patterns are obvious:

  • Loading all tool definitions up front is preloading the disk into cache. The agent pays for hundreds of tools to use three.
  • Passing large tool results through the model is moving data through the CPU registers when a direct copy between devices would do. That's the transcript example: the model was a very expensive copy loop.
  • Letting conversation history grow forever is a cache with no eviction policy.

The fixes are also familiar. Anthropic's write-up calls the first one progressive disclosure: present tools as a filesystem so the model can list what exists and read a definition only when it needs it. That's demand paging. Running code that keeps intermediate data in the sandbox is the equivalent of direct memory access: data moves between tools without passing through the processor. Summarizing or dropping old turns is eviction.

There's a quality argument too, not only a cost one. The "Lost in the Middle" study found that models use information at the beginning and end of a long context much better than information in the middle[3]. An overstuffed cache isn't just slow. It has worse hit rates.

The Evidence

The headline numbers come from Anthropic's write-up: tool-definition tokens down from 150,000 to 2,000 by loading definitions on demand, and an estimated 50,000 tokens saved on a single long transcript by keeping it out of the model. Both came from changing how the agent reaches its tools, not from changing the model[1]. Cloudflare reported the same direction of result for Code Mode, arguing that models are better at writing code against a typed API than at making many separate tool calls, because they've seen vastly more real-world code than synthetic tool-call examples[2].

Anthropic's earlier guide to writing tools for agents makes the same point at the design level[4]. It recommends fewer, more purposeful tools and responses that return only high-signal information, with pagination and filtering instead of raw dumps. That's cache-line design: make each fetch carry the data you actually use.

The trade-off is stated plainly in the source, too. Running agent-written code requires a secure sandbox with resource limits and monitoring, and that is real operational overhead that direct tool calls avoid[1].

Grain of Salt

The obvious objection: context windows keep growing and per-token prices keep falling. Why engineer around a constraint that's disappearing? Plus, prompt caching already makes repeated tool definitions cheap.

Two answers. First, cheaper tokens don't fix the quality problem: a bigger, fuller context still buries the instructions that matter. Second, prompt caching makes a stable prefix cheaper to re-read, but the model still has to attend to it, and large tool results that change on every call can't be cached at all. Cheaper L1 is still L1. Wasting it was a mistake even when CPUs got faster.

What would prove this wrong? Evidence that agents with all tools preloaded match the accuracy of progressive-disclosure agents as tool counts grow into the hundreds. So far, the published evidence points the other way.

Set an Eviction Policy

  1. Measure what's in the window. Log token counts per request, broken into system prompt, tool definitions, conversation history, and tool results. Most teams discover that tool definitions or raw tool output dominate.
  2. Cut and merge tools. Follow Anthropic's tool-writing guidance: fewer, task-shaped tools beat a one-to-one wrapper around every API endpoint[4]. Remove tools that haven't been called in 30 days.
  3. Return less from tools. Add filtering, pagination, and a concise response mode to your highest-volume tools. Return IDs and summaries by default and full payloads only on request.
  4. Load tool definitions on demand. Expose a small search or list tool that returns tool names and one-line descriptions, and load full schemas only for the tools the agent picks.
  5. Move bulk data outside the model. For workflows that shuttle data between systems, let the agent write code that runs in a sandbox and returns only a result summary. Budget for the sandbox: isolation, resource limits, and logs are part of the cost.

First 24 Hours

Take your busiest agent and log one full request. Count the tokens in tool definitions, then count how many of those tools the agent actually called. Divide the second number by the first. That's your cache hit rate, and it's probably below 10%.
